# 旅图 · Travel Notes to Map

> 旅图想做的事情很简单：把你已经收藏的攻略，摊到真实地图上，再一步步变成能走的行程。

## 为什么做它

这个项目来自一个很常见的旅行场景：出发前，我们往往已经在小红书、朋友圈或其他平台收藏了很多攻略，也大概知道自己想去哪些地方；但真正开始排行程时，仍然需要手动把零散的地点重新整理、在地图上一个个搜索、判断彼此距离，再考虑每天怎么分组、路线是否顺路、途中吃什么、住在哪里更方便。

旅图想解决的不是“让 AI 再生成一份旅游攻略”，而是把用户已经产生的兴趣和已经收藏的信息，进一步转化为真实、可执行的旅行计划。

用户负责“种草”，系统负责把这些碎片化内容落到真实地图上，并结合地点、距离、路线和用户自己的调整，逐步形成可以直接拿来走的行程。

因此，它的分工很明确：AI 负责理解非结构化的攻略文本和截图；地图与规则负责真实世界的位置、路线和约束；用户始终保有对地点、天数、顺序、餐厅和住宿的最终控制权。

最终希望呈现的是一种更接近“旅行工作台”的体验：从攻略截图和文本开始，经过地点识别、真实 POI 对齐、多日行程生成、路线规划、手动调整，再到沿途餐饮和住宿建议，把“收藏了很多攻略”真正变成“我知道这几天该怎么走”。

## 现在能做什么

### 1. 从攻略开始，而不是从空白计划开始

可以粘贴攻略文本、上传多张攻略截图，或两者一起使用。输入区提供灰色示例作为起点，但示例不会被当成真实输入，也不会自动提交。

系统会从内容中提取被推荐、具有游览价值的地点，并保留地点类型、推荐理由、预计停留时间、攻略提示与推荐程度等信息。它不会把所有在交通描述中偶然出现的地点都当作必去景点。

### 2. 把模糊地点落到真实地图

提取出的名称会交给高德地图进行真实 POI 搜索，得到名称、地址、经纬度与 POI 标识，再展示为地图 Marker。

- 已确认的地点直接上图；
- 存在多个合理候选时，交给用户确认，不擅自选择第一个结果；
- 搜索失败不会让整个计划中断，其他已找到地点仍可继续使用；
- 不同类型的地点使用不同的 Marker 视觉，方便在地图上区分景点、餐饮、住宿与交通。

这一步的意义在于：后面的距离、路线和住宿建议，都基于真实 POI，而不是模型猜测的坐标。

### 3. 从地点清单生成多日行程

在确认地点后，用户可以设置目的地、旅行天数与节奏。系统会结合地点数量、停留时长、必去标记与地理位置，把地点分配到不同日期，并生成每一天建议的访问顺序。

每段相邻地点之间会尝试获取高德真实通勤信息，并在地图上绘制路线。若某一段路线未能取得，界面会明确说明“路线暂未获取”，而不会伪造直线或错误路线。

### 4. 计划可以被用户随时接管

自动规划只是初稿，不是最终答案。用户可以：

- 删除不想去的地点，或按推荐程度筛选；
- 手动搜索并添加真实地点；
- 将地点放入某一天、移出当天或放回“暂未安排”；
- 跨天移动地点；
- 在同一天内拖拽调整游览顺序；
- 修改停留时长、标记必去地点。

这些动作会保留用户刚刚做出的安排，并只刷新受影响日期的路线信息，避免重新计算时把用户的顺序改回去。

### 5. 把“路上”也纳入考虑

当两点间通勤较长时，旅图会在路线中提示“路上找点吃的”。如果路线的起点或终点本身已经是餐饮地点，则不会重复推荐吃饭。

完成行程后，还可以根据每天行程的地理重心推荐适合住宿的区域，并提供附近酒店候选。酒店信息会尽量展示地图可提供的参考字段，例如评分、参考消费和距离地铁；某项数据缺失时不会硬编出来。

## 一次典型使用流程

```text
粘贴攻略 / 上传截图
        ↓
识别被种草的地点
        ↓
高德真实 POI 确认与候选选择
        ↓
地图查看、筛选、增删地点
        ↓
生成多日行程与真实通勤路线
        ↓
拖拽调整顺序、补充餐饮与住宿
        ↓
得到可继续编辑、可以照着走的旅行计划
```

## 设计原则

1. **从用户已有兴趣出发**：不替用户凭空决定“应该去哪里”。
2. **真实世界的信息交给地图**：地点、坐标、地址、通勤路线以高德返回结果为准。
3. **自动化给建议，用户做决定**：候选地点、必去程度、日程分配与顺序都可由用户调整。
4. **失败可见且局部可用**：一个地点或一段路线失败，不阻塞其他部分继续工作。
5. **不伪造数据**：没有真实 POI、路线、评分或价格时，明确不展示或标记未获取。

## 运行项目

### 环境要求

- Node.js 18 或以上
- 高德 Web JS API Key 与安全密钥
- 兼容 OpenAI 接口格式的模型服务 Key（默认配置为通义千问 DashScope）

### 安装与配置

```bash
npm install
cp .env.example .env
```

在 `.env` 中填写：

```env
VITE_AMAP_KEY=
VITE_AMAP_SECURITY_CODE=

LLM_API_KEY=
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus
LLM_VISION_MODEL=qwen-vl-plus
```

高德控制台中应创建 **Web 端（JS API）** 应用。开发环境一般使用 `http://127.0.0.1:5173`；部署时请按高德控制台要求配置实际域名白名单。

### 启动

```bash
npm run dev
```

打开终端显示的本地地址（默认是 <http://127.0.0.1:5173>）。

```bash
npm run build
```

可进行 TypeScript 与生产构建检查。

## 项目结构

```text
src/
├── main.ts                 # 页面状态与主要交互编排
├── map-view.ts             # 高德地图、Marker 与路线绘制
├── poi-resolver.ts         # 地点名称 → 真实 POI
├── poi-dedup.ts            # 相同 POI 的去重与信息合并
├── ai-extraction.ts        # 解析文本与截图的前端调用层
├── day-grouping.ts         # 多日地点分组
├── route-planning.ts       # 日内顺序与路线结果组织
├── amap-route-service.ts   # 高德真实通勤路线
├── along-route-food.ts     # 沿途餐饮建议
├── stay-recommendations.ts # 住宿区域与酒店候选
└── types.ts                # 核心数据结构

server/
├── index.mjs               # 本地服务、模型请求代理与重试
└── ai/prompts/             # 攻略提取与内容摘要提示词
```

浏览器只处理页面和地图交互；模型 Key 由本地服务读取，不使用 `VITE_` 前缀，也不会进入浏览器打包产物。`.env` 已被 Git 忽略，不应提交真实 Key。

## 当前定位与边界

旅图目前重点验证“攻略碎片 → 真实地点 → 可编辑行程”的完整体验。它没有账号体系、云端数据库、多人协作或线上订单能力；行程、酒店与餐饮建议也应被视为辅助决策，而不是预订或价格承诺。
